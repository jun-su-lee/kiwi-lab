## 퀴즈

**Q1. 보낸 순서와 다르게 받은 이유, 같은 주문 ID의 순서를 지키려면?** — 4/5
> 키 설정을 하지 않아서. 카프카는 동일 파티션 내 순서는 보장하지만 토픽 전체 순서는 보장하지 않는다. 같은 파티션으로 보내려면 같은 키를 가져야 한다.

부족한 부분: "주문 ID를 메시지 키로 쓴다"는 구체적인 해법까지 말하면 완벽. 키가 없으면 이벤트가 여러 파티션에 흩어지고, 컨슈머는 파티션들을 섞어 읽기 때문에 순서가 뒤바뀐다는 흐름도 덧붙이면 좋음. (심화: 파티션 수를 늘리면 `hash % 파티션 수`가 바뀌어 같은 키도 다른 파티션으로 갈 수 있음 / 재시도 시 파티션 안에서도 순서가 뒤집힐 수 있음 → 3장)

**Q2. 파티션 3개 토픽을 컨슈머 5개 그룹이 읽으면? 처리 속도를 더 높이려면?** — 5/5
> 3개 컨슈머가 파티션 하나씩 담당, 2개는 유휴. 속도를 높이려면 파티션을 5개 이상으로 늘린다.

보충: 파티션 수는 늘릴 수만 있고 줄일 수 없음. 늘리면 키 → 파티션 매핑이 바뀌어 키 기반 순서가 깨질 수 있으니(Q1과 연결), 키를 쓰는 토픽은 1~2년 뒤 목표 처리량 기준으로 약간 넉넉하게 잡는 것이 흔한 관행([Confluent 블로그, Jun Rao](https://www.confluent.io/blog/how-choose-number-topics-partitions-kafka-cluster/) — 최소 `max(목표처리량/파티션당 프로듀스 처리량, 목표처리량/파티션당 컨슘 처리량)`). 단 너무 많으면 파일 핸들·장애 복구 시간·지연·클라이언트 메모리 비용이 늘어남. 책 2장 "파티션 수 결정하기"에서 다시 다룸. 유휴 컨슈머는 평상시엔 자원만 쓰는 낭비. 장애 시 리밸런스로 파티션을 받을 수 있지만, 유휴 컨슈머가 없어도 남은 컨슈머들이 나눠 가지므로 "대기 인력" 효과는 장애 후에도 컨슈머당 파티션 1개를 유지하는 정도로 제한적.

**Q3. 일반 메시지 큐와 카프카의 가장 큰 차이 두 가지는?** — 5/5
> 다중 컨슈머: 여러 컨슈머 그룹이 한 토픽을 독립적으로 읽을 수 있음. 디스크 기반 영속성: 컨슈머가 늦게 읽어도, 프로듀서와 컨슈머의 처리 속도가 달라도 문제없음.

보충: 일반 큐와 대비하면 더 선명함 — 일반 큐는 한 컨슈머가 가져가면 메시지가 사라지고, 카프카는 읽어도 보존 기간까지 남아 있음. 그래서 오프셋을 되돌려 과거 데이터를 다시 읽는(재처리) 것도 가능.

**Q4. 리더와 팔로워의 역할은? 리더 브로커가 죽으면 누가 무엇을 하나?** — 4/5
> 파티션은 여러 브로커에 분산 저장되어 가용성을 보장. 쓰기가 가능한 파티션을 가진 브로커가 리더, 복제하는 브로커가 팔로워. 리더 브로커가 죽으면 컨트롤러가 감지하고 다른 브로커를 리더로 한다.

부족한 부분:
- "분산 저장"보다 "복제" — 파티션 하나를 쪼개 나눠 담는 게 아니라, 같은 파티션의 전체 사본(레플리카)을 여러 브로커에 둔다.
- 리더/팔로워는 브로커 단위가 아니라 파티션(레플리카) 단위 역할. 한 브로커가 P0의 리더이면서 P1의 팔로워일 수 있다.
- 새 리더는 아무 브로커나가 아니라 ISR(리더를 잘 따라잡고 있던 팔로워) 중에서 뽑는다. 그래야 데이터 유실이 없다.
- 컨트롤러가 바뀐 리더 정보를 전파해야 클라이언트가 새 리더로 붙는다.
- 읽기도 기본적으로 리더가 처리.

**Q5. 시간 기준 보존과 로그 압착은 각각 어떤 데이터에 어울리나? (예시 포함)** — 3/5
> 시간 기준 보존은 주어진 기간만큼 저장하고 싶은 데이터. 로그 압착은 최근 업데이트 내역을 보고자 하는 데이터.

부족한 부분:
- 요청한 예시가 없음. 정의를 다시 말한 수준.
- "최근 업데이트 내역"은 모호함. 압착은 내역(이력)을 남기는 게 아니라 **키별 마지막 값 하나만** 남겨 현재 상태를 유지하는 것. 중간 이력은 사라진다.
- 예시) 시간 기준: 클릭 이벤트, 애플리케이션 로그 — 일정 기간 지나면 필요 없음. 압착: 사용자별 프로필/설정, 상품별 현재 재고 — 키(사용자 ID)별 최신 값만 필요.
- 시험 포인트: 카프카 내부 토픽 `__consumer_offsets`(컨슈머 그룹 오프셋)와 Kafka Connect의 config/offset/status 토픽이 압착 토픽. 값이 null인 메시지(툼스톤)를 보내면 해당 키가 삭제된다.

**Q6. KRaft 컨트롤러 3대면 몇 대 장애까지 견디나? 이유는? 4대로 늘리면 나아지나?** — 0/5
> 모르겠음.

정답: 1대까지. 컨트롤러 쿼럼은 과반수(`n/2 + 1`, 소수점 버림)가 살아 있어야 리더를 뽑고 메타데이터 변경을 확정할 수 있다. 3대의 과반수는 2대 → 1대 장애 허용. 4대의 과반수는 3대 → 여전히 1대만 허용, 장애 날 노드만 늘어나므로 손해. 5대면 과반수 3대 → 2대 허용. 그래서 홀수(3 또는 5)로 구성한다.
과반수가 필요한 이유: 네트워크가 둘로 갈라졌을 때 양쪽이 각자 리더를 뽑는 split-brain을 막기 위해. 과반수 두 집합은 반드시 겹치므로 리더는 하나뿐이다.
(1장 본문 범위 밖 — 컨트롤러 질문 때 정리한 KRaft 보강 내용. 6장에서 다시 확인)

**1장 합계: 21/30** — 약점: 로그 압착 개념(키별 마지막 값), KRaft 쿼럼 과반수.

## 추가 질문

**로그 압착의 주기는?** — 고정 주기가 아니라 조건 기반 (6장에서 자세히)
- 브로커의 log cleaner 스레드가 백그라운드에서 돈다. 할 일이 없으면 `log.cleaner.backoff.ms`(15초)만큼 쉬고 다시 확인.
- **활성 세그먼트는 압착 대상이 아님.** 세그먼트가 닫혀야(`segment.bytes` 1GB 또는 `segment.ms` 7일) 대상이 된다.
- 닫힌 세그먼트 중 아직 압착 안 된 부분(dirty) 비율이 `min.cleanable.dirty.ratio`(0.5) 이상인 파티션부터 압착.
- `min.compaction.lag.ms`(0): 메시지가 최소 이 시간은 압착되지 않고 남음.
- `max.compaction.lag.ms`(무한대): 이 시간이 지나면 dirty 비율과 무관하게 압착 대상.
- `delete.retention.ms`(24시간): 툼스톤이 압착 후에도 남아 있는 시간. 컨슈머가 삭제를 볼 기회를 준다.
- 함정: 트래픽이 적은 토픽은 세그먼트가 안 닫혀서 7일 동안 압착이 전혀 안 될 수 있다.
