카프카 설치하기

2장은 설정값 사전이다. 설정 이름, 기본값, 그리고 "그 값을 바꾸면 무슨 일이 생기나"를 외워야 하는 장이고, 시험에서 비중이 가장 큰 도메인과 바로 이어진다.

2.1환경 설정하기

운영체제, 자바, 그리고 (책 기준) 주키퍼

  • 운영체제: 리눅스를 권장한다. 운영 환경 대부분이 리눅스이고, 뒤에 나오는 커널 튜닝도 리눅스 기준이다.
  • 자바: 카프카는 JVM 위에서 돈다. Kafka 4.0부터 브로커는 Java 17 이상, 클라이언트는 Java 11 이상이 필요하다.
  • 주키퍼: 책은 브로커보다 주키퍼를 먼저 띄운다. 단독 서버 하나로도 되지만, 운영에서는 3대 또는 5대의 앙상블을 쓴다. 과반수가 살아야 동작하기 때문에 홀수로 구성한다.
책과 현재 버전 차이

Kafka 4.x에는 주키퍼가 없다. 주키퍼 앙상블 대신 KRaft 컨트롤러 쿼럼을 띄운다. "과반수가 살아야 하니 홀수로"라는 원리는 1장 복습에서 본 KRaft와 똑같다. 주키퍼 설치 절은 원리만 이해하고 넘어가면 된다.

2.2카프카 브로커 설치하기

압축 풀고, 설정 파일 고치고, 실행

책의 흐름은 단순하다. 배포판 압축을 풀고 config/server.properties를 고친 뒤 kafka-server-start.sh로 띄운다. 그다음 토픽을 만들고, 콘솔 프로듀서로 쓰고, 콘솔 컨슈머로 읽어서 동작을 확인한다.

# KRaft (4.x) 기준 설치 순서
kafka-storage.sh random-uuid → 클러스터 ID 생성
kafka-storage.sh format -t <클러스터ID> -c server.properties
kafka-server-start.sh server.properties
kafka-topics.sh --create --topic test --partitions 3 --replication-factor 1 --bootstrap-server localhost:9092
시험 포인트

KRaft에서는 브로커를 처음 띄우기 전에 kafka-storage.sh format으로 로그 디렉터리를 포맷해야 한다. 이 단계에서 클러스터 ID가 기록된다. 주키퍼 시절에는 없던 단계라 책에는 없다. 또 CLI 도구는 --zookeeper가 아니라 --bootstrap-server로 브로커에 붙는다.

2.3브로커 설정하기 ★

2장의 핵심. 설정 이름과 기본값을 같이 기억하자

핵심 브로커 설정

broker.idKRaft: node.id

클러스터 안에서 브로커마다 겹치지 않아야 하는 정수 ID. 호스트 이름과 맞춰 두면 운영이 편하다(예: kafka3 → 3).

listeners예: PLAINTEXT://:9092

브로커가 연결을 받을 주소와 포트. 이름://호스트:포트 형식이고 여러 개를 쉼표로 둘 수 있다. 이름과 보안 프로토콜의 짝은 listener.security.protocol.map으로 정한다. 클라이언트에게 알려줄 주소는 advertised.listeners로 따로 지정한다.

kiwi-lab: Strimzi가 plain 리스너(9092, TLS 없음)를 만든다.
log.dirs기본 /tmp/kafka-logs

메시지를 저장할 디렉터리. 여러 개를 쉼표로 줄 수 있다. 새 파티션은 파티션 개수가 가장 적은 디렉터리에 놓인다. 남은 디스크 용량 기준이 아니다.

num.recovery.threads.per.data.dir기본 1

브로커가 시작하거나 종료할 때 로그 세그먼트를 열고 닫는 스레드 수. 디렉터리마다 이만큼 생긴다. 8로 두고 log.dirs가 3개면 스레드는 24개. 비정상 종료 뒤 재시작이 느릴 때 늘린다.

auto.create.topics.enable기본 true

없는 토픽에 프로듀서가 쓰거나, 컨슈머가 읽거나, 메타데이터를 요청하면 토픽을 자동으로 만든다. 오타 하나로 토픽이 생기므로 운영에서는 보통 끈다.

kiwi-lab: "true"로 켜져 있다(학습용).
auto.leader.rebalance.enable기본 true

리더가 한 브로커에 쏠리면 주기적으로 선호 리더(1장에서 본 원래 배치)로 되돌린다. 확인 주기는 leader.imbalance.check.interval.seconds(300초), 기준은 leader.imbalance.per.broker.percentage(10%).

delete.topic.enable기본 true

토픽 삭제 허용 여부. 실수로 지우는 걸 막고 싶으면 끈다.

process.roles · controller.quorum.votersKRaft 전용 책에 없음

process.roles는 이 노드가 broker, controller, 또는 둘 다인지 정한다. 컨트롤러 쿼럼 구성원은 controller.quorum.voters(고정 목록) 또는 controller.quorum.bootstrap.servers로 알려준다. 컨트롤러끼리 쓰는 리스너 이름은 controller.listener.names.

kiwi-lab: roles: [controller, broker] → combined 모드.

토픽별 기본값

아래는 브로커에 두는 기본값이다. 토픽을 만들 때 토픽별로 덮어쓸 수 있고, 그때 이름이 조금 달라진다(예: 브로커 log.retention.ms → 토픽 retention.ms).

num.partitions기본 1

자동 생성되는 토픽의 파티션 수. 파티션은 늘릴 수만 있고 줄일 수 없다(1장 복습 R4).

default.replication.factor기본 1

자동 생성되는 토픽의 복제 팩터. 책은 min.insync.replicas보다 최소 1 크게, 보통 3을 권한다. 1이면 브로커 하나만 죽어도 그 파티션은 끝이다.

kiwi-lab: 브로커가 1대라 1. 내부 토픽 offsets.topic.replication.factor(기본 3)도 1로 낮춰 두었다.
log.retention.ms / minutes / hours기본 168시간(7일)

메시지 보존 시간. 세 개를 같이 설정하면 단위가 작은 쪽(ms)이 이긴다.

log.retention.bytes기본 -1 (무제한)

보존 크기. 파티션 단위다. 파티션 8개 토픽에 1GB로 두면 토픽 전체로는 최대 8GB. 시간과 크기를 둘 다 설정하면 먼저 걸리는 쪽으로 지운다.

log.segment.bytes기본 1GB

세그먼트 파일 하나의 최대 크기. 이 크기가 차면 세그먼트를 닫고 새로 연다. 보존 기간은 닫힌 세그먼트 단위로 적용된다.

log.roll.ms / log.roll.hours기본 168시간

크기와 상관없이 이 시간이 지나면 세그먼트를 닫는다. 크기와 시간 중 먼저 걸리는 쪽이 적용된다.

min.insync.replicas기본 1

프로듀서가 acks=all로 쓸 때, 최소 몇 개의 ISR이 메시지를 받아야 성공으로 칠지. 복제 팩터 3이면 보통 2로 둔다. ISR이 이보다 적으면 쓰기가 거부된다.

message.max.bytes기본 약 1MB

브로커가 받는 메시지(배치) 최대 크기, 압축 후 기준. 토픽별로는 max.message.bytes. 늘리면 브로커 간 복제용 replica.fetch.max.bytes와 컨슈머의 fetch 크기도 함께 맞춰야 한다.

보존은 세그먼트 단위로 지운다

보존 7일이라고 메시지가 정확히 7일 뒤에 지워지는 게 아니다. 세그먼트가 닫히고, 그 세그먼트의 마지막 메시지가 7일이 지나야 세그먼트 파일째로 지운다. 1장 압착 질문에서 본 "활성 세그먼트는 건드리지 않는다"와 같은 원리다.

레플리카를 눌러 브로커를 죽여 보자. acks=all 프로듀서의 쓰기가 성공하는지 확인한다.

2.4하드웨어 선택하기

카프카는 디스크와 페이지 캐시로 먹고산다

디스크 처리량

  • 프로듀서 지연에 가장 직접 영향을 준다.
  • 메시지가 디스크에 써져야 커밋되기 때문.
  • SSD가 유리, HDD는 여러 개로 나눠 쓴다.

디스크 용량

  • 하루 유입량 × 보존 기간 × 복제 팩터.
  • 여유분 10% 이상을 더 잡는다.
  • 아래 계산기로 감을 잡자.

메모리

  • JVM 힙은 크지 않아도 된다(수 GB).
  • 남는 메모리는 OS 페이지 캐시로 쓰여 컨슈머 읽기를 빠르게 한다.
  • 다른 애플리케이션과 같이 두지 않는다.

네트워크 · CPU

  • 나가는 트래픽이 들어오는 것보다 크다(복제 + 여러 컨슈머 그룹).
  • CPU는 주로 압축 해제·재압축에 쓰여 병목이 되는 일이 적다.
직접 해보기 · 디스크 용량

하루 유입량과 보존 기간으로 클러스터 전체와 브로커당 필요한 디스크를 계산한다.

2.5클라우드에서 카프카 사용하기

가볍게 읽고 넘어가도 되는 절

Azure, AWS에서 인스턴스와 디스크를 고를 때도 기준은 같다. 보존할 데이터 양, 프로듀서가 요구하는 성능을 먼저 정하고 디스크 종류와 인스턴스를 고른다. 원격 디스크는 지연이 크고 로컬 디스크는 인스턴스와 함께 사라질 수 있다는 트레이드오프가 핵심이다. 관리형 서비스(Confluent Cloud 등)를 쓰면 이 고민을 맡길 수 있다.

2.6카프카 클러스터 설정하기

브로커 몇 대? 그리고 리눅스 튜닝

브로커 수 정하기

  • 디스크 용량: 위 계산기의 클러스터 전체 용량 ÷ 브로커 한 대의 디스크.
  • 레플리카 수: 브로커 한 대가 감당하는 파티션 레플리카에는 한계가 있다. 책은 브로커당 약 14,000개, 클러스터 전체 약 100만 개 이하를 권한다.
  • 네트워크·CPU: 트래픽이 몰리는 시간대 기준으로 여유를 둔다.

파티션 수 정하기

1장 Q2에서 이야기한 그 주제다. 목표 처리량을 파티션 하나의 처리량으로 나눠서 계산하고, 키를 쓰는 토픽이면 나중을 생각해 약간 여유를 둔다. 책은 디스크 기준으로 파티션 하나가 하루에 6GB를 넘지 않게 하라는 경험칙도 제시한다.

2.7프로덕션 환경에서의 고려사항

GC, 랙 배치, 주키퍼 공유

  • GC: G1GC를 쓴다. 책은 MaxGCPauseMillis=20, InitiatingHeapOccupancyPercent=35처럼 기본값보다 공격적인 값을 예로 든다. 힙은 크지 않게 두고 남는 메모리는 페이지 캐시에 양보한다.
  • 랙 배치: 브로커에 broker.rack을 지정하면 파티션을 만들 때 레플리카를 서로 다른 랙(클라우드라면 가용 영역)에 나눠 둔다. 랙 하나가 통째로 죽어도 파티션이 살아남는다.
  • 주키퍼 공유: 책은 여러 카프카 클러스터가 주키퍼 앙상블 하나를 같이 써도 되지만, 카프카 외 애플리케이션과 공유하지는 말라고 한다. KRaft에서는 해당 없음.
시험 포인트
  • 보존 설정 우선순위: ms > minutes > hours.
  • log.retention.bytes는 파티션 단위, 시간과 크기는 먼저 걸리는 쪽.
  • log.dirs에 새 파티션은 파티션 수가 적은 디렉터리로.
  • 복제 팩터 3 + min.insync.replicas=2 + acks=all이 표준 조합. 브로커 1대 장애까지 쓰기 가능.
  • KRaft: process.roles, node.id, controller.quorum.voters, 첫 기동 전 kafka-storage.sh format.

Q자가 점검

2장을 읽은 뒤 이 질문으로 퀴즈를 진행한다

  1. log.retention.hours=168과 log.retention.ms=3600000을 같이 설정하면 보존 기간은?
  2. 파티션 10개 토픽에 log.retention.bytes=1GB를 설정했다. 이 토픽이 디스크에 최대 얼마까지 쌓일 수 있나?
  3. 복제 팩터 3, min.insync.replicas=2, acks=all에서 브로커가 몇 대까지 죽어도 쓰기가 되나?
  4. log.dirs에 디렉터리가 3개 있다. 새 파티션은 어디에 놓이나?
  5. 운영 환경에서 auto.create.topics.enable을 끄는 이유는?
  6. KRaft 클러스터를 처음 띄울 때 브로커 시작 전에 꼭 해야 하는 단계는?
