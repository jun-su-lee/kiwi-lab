카프카 시작하기

카프카는 여러 시스템이 데이터를 주고받는 중앙 우체국이고, 받은 편지를 버리지 않고 순서대로 쌓아두는 기록 장부다.

1.1발행/구독 메시지 전달

왜 중간에 무언가를 두는가

처음엔 서버 A가 지표를 서버 B로 바로 보낸다. 간단하다. 그런데 보내는 쪽과 받는 쪽이 늘어나면 연결선이 보내는 쪽 수 × 받는 쪽 수만큼 늘어난다.

  • 발행자(publisher)는 누가 받을지 모른 채 게시판에 글을 올린다.
  • 구독자(subscriber)는 관심 있는 주제의 글만 가져간다.
  • 서로 몰라도 되니 결합도가 낮아진다.

그런데 지표용 큐, 로그용 큐, 사용자 활동용 큐처럼 게시판이 용도별로 또 여러 개 생긴다. 범용 게시판 하나로 전부 처리하자는 것이 카프카의 출발점이다.

1.2카프카 입문

이후 모든 장에서 쓰이는 용어. 이 절이 1장의 핵심이다.

메시지와 배치

용어비유설명
메시지편지 한 통카프카의 데이터 단위. 카프카는 내용을 해석하지 않고 바이트 배열로만 다룬다.
키봉투의 주소선택값. 같은 키는 같은 파티션으로 가게 하는 데 쓴다.
배치우체통에 모았다가 한 번에 수거같은 토픽·파티션으로 갈 메시지를 묶어서 보낸다.

배치는 처리량과 지연의 맞교환이다. 크게 묶으면 네트워크 왕복이 줄어 처리량이 오르지만 메시지 하나가 기다리는 시간은 늘어난다. 3장에서 linger.ms, batch.size로 다시 나온다.

스키마

카프카는 메시지 내용을 모르기 때문에 보내는 쪽과 받는 쪽이 형식을 약속해야 한다. JSON은 읽기 쉽지만 타입이 느슨하고 형식이 바뀌면 깨지기 쉽다. 책은 스키마가 바뀌어도 호환성을 유지하는 Avro를 권한다. 스키마를 한곳에 모아두는 저장소가 Schema Registry이고, kiwi-lab에도 띄워져 있다.

토픽과 파티션 ★

토픽은 메시지를 분류하는 이름(DB의 테이블에 해당)이고, 파티션은 토픽을 쪼갠 단위다. 파티션 하나는 끝에만 덧붙이고 처음부터 순서대로 읽는 커밋 로그다. 각 칸의 번호가 오프셋이다.

토픽 debezium.mysql.local.testdb.orders
P0
0123
← 쓰기는 항상 끝에
P1
012
P2
01234
칸 안의 숫자 = 오프셋. 파티션마다 0부터 따로 센다.
시험 포인트
  • 순서는 파티션 안에서만 보장된다. 토픽 전체 순서는 보장되지 않는다.
  • 파티션을 여러 브로커에 나눠 두면 확장성, 복제해 두면 가용성을 얻는다.
  • 스트림은 보통 파티션 수와 무관하게 토픽 하나의 데이터 흐름을 가리킨다.

프로듀서와 컨슈머

프로듀서는 메시지를 쓰는 쪽이다. 키가 없으면 파티션에 고르게 퍼뜨리고, 키가 있으면 키의 해시값으로 파티션을 고른다. 그래서 같은 키는 항상 같은 파티션에 들어가고, 그 키의 순서가 지켜진다.

직접 해보기 · 키 → 파티션

카프카 기본 파티셔너와 같은 murmur2 해시로 계산한다. 같은 주문 ID를 여러 번 보내면 늘 같은 줄에 쌓이는 걸 확인해보자.

파티션 수
3

컨슈머는 메시지를 쓰인 순서대로 읽는다. 어디까지 읽었는지는 오프셋으로 기억하는데, 일종의 책갈피다. 컨슈머가 재시작해도 저장된 오프셋부터 이어 읽는다.

컨슈머 그룹 ★

여러 컨슈머가 한 팀(그룹)이 되어 토픽을 나눠 읽는다. 규칙은 하나다. 그룹 안에서 파티션 하나는 컨슈머 하나만 읽는다.

직접 해보기 · 컨슈머 그룹

파티션 4개짜리 토픽을 그룹 하나가 읽는다. 컨슈머 수를 바꿔보면 파티션이 다시 나눠진다(리밸런스, 4장).

컨슈머 수
3
  • 컨슈머 하나가 죽으면 그 파티션을 남은 컨슈머가 나눠 가진다.
  • 컨슈머가 파티션보다 많으면 남는 컨슈머는 논다.
  • 다른 그룹은 같은 토픽을 서로 간섭 없이 처음부터 다 읽을 수 있다. 일반 큐와 가장 다른 점이다.

브로커와 클러스터

용어설명
브로커카프카 서버 한 대. 메시지를 받아 오프셋을 붙이고 디스크에 저장하며, 컨슈머의 읽기 요청에 응답한다.
클러스터브로커 여러 대의 묶음.
컨트롤러클러스터 관리자. 파티션을 어느 브로커에 둘지 정하고 브로커 장애를 감지한다.
리더파티션마다 하나. 쓰기와 (기본적으로) 읽기를 맡는다.
팔로워리더를 복제만 하다가, 리더가 죽으면 그중 하나가 새 리더가 된다.
브로커 1
P0리더
P1팔로워
P2팔로워
브로커 2
P0팔로워
P1리더
P2팔로워
브로커 3
P0팔로워
P1팔로워
P2리더

리더를 브로커마다 골고루 두어 부하를 나눈다. 브로커 1이 죽으면 P0의 리더는 브로커 2나 3의 팔로워가 이어받는다.

보존(retention)

카프카는 컨슈머가 읽어도 메시지를 바로 지우지 않는다. 대신 정해진 기준에 따라 오래된 것부터 지운다.

방식기준어울리는 데이터
시간 기준예: 7일이 지나면 삭제로그, 이벤트처럼 일정 기간만 필요한 것
크기 기준예: 파티션이 1GB를 넘으면 오래된 것부터 삭제디스크 용량을 지켜야 할 때
로그 압착같은 키의 마지막 값만 남김사용자별 최신 상태처럼 "현재 값"만 필요한 것 (6장)
책과 현재 버전 차이

책(2판)은 ZooKeeper가 컨트롤러를 뽑고 클러스터 메타데이터를 저장한다고 설명한다. Kafka 4.0부터 ZooKeeper는 완전히 제거되었고, 브로커 중 일부가 컨트롤러 역할을 맡아 메타데이터를 카프카 로그로 관리하는 KRaft만 쓴다. kiwi-lab 클러스터도 strimzi.io/kraft: enabled인 KRaft 클러스터다. 시험에는 KRaft 문제가 나오므로 6장에서 따로 보강한다.

다중 클러스터

클러스터를 여러 개 두는 이유는 세 가지다.

  • 데이터 종류 분리: 용도별로 격리한다.
  • 보안 요구사항 분리: 민감한 데이터는 별도 클러스터에 둔다.
  • 다중 데이터센터: 재해 복구나 지역별 서비스에 쓴다.

클러스터 사이에 데이터를 복사하는 도구가 미러메이커(MirrorMaker)다. 원리는 한쪽에서 읽어서 다른 쪽에 쓰는 것뿐이다. 10장에서 자세히 다룬다.

1.3왜 카프카인가?

다른 메시지 시스템 대신 카프카를 고르는 이유

장점의미
다중 프로듀서여러 시스템이 같은 토픽에 동시에 쓸 수 있다.
다중 컨슈머여러 그룹이 같은 데이터를 서로 간섭 없이 읽는다. 일반 큐는 한 명이 읽으면 사라진다.
디스크 기반 보존컨슈머가 느리거나 잠시 죽어도 데이터가 남아 있어서, 나중에 따라잡으면 된다.
확장성브로커 한 대로 시작해 운영 중단 없이 늘릴 수 있다.
고성능순차 디스크 쓰기와 배치 덕분에 대용량에서도 지연이 낮다.
플랫폼 기능Kafka Connect(외부 시스템 연동), Kafka Streams(스트림 처리) 같은 도구가 함께 있다.

1.4데이터 생태계

카프카는 시스템 사이를 잇는 순환계 역할을 한다

kiwi-lab이 바로 이 구조다.

MySQLDebezium →KafkaS3 Sink →MinIO (S3)
사용 사례예시
활동 추적클릭, 페이지뷰 같은 사용자 행동 수집. 링크드인이 카프카를 만든 원래 목적.
메시지 교환이메일, 알림 발송 요청 전달.
지표·로그 수집여러 서버의 로그를 한곳으로 모은다.
커밋 로그DB 변경사항(CDC)을 흘려보내 다른 시스템에 복제한다. Debezium이 하는 일.
스트림 처리흐르는 데이터를 실시간으로 집계·변환한다 (14장).

1.5카프카의 기원

가볍게 읽고 넘어가도 되는 절

  • 링크드인에서 사용자 활동과 지표 수집 문제를 풀려고 만들었다. 제이 크렙스, 네하 나크헤데, 준 라오가 주도했다.
  • 2011년 오픈소스로 공개되어 아파치 프로젝트가 됐다. 이후 창시자들이 이 시험을 주관하는 Confluent를 세웠다.
  • 이름은 작가 프란츠 카프카에서 따왔다. 쓰기에 최적화된 시스템이라 작가 이름이 어울린다는 이유였다.
