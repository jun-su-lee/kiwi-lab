## 1.1 발행/구독 메시지 전달

직접 연결은 보내는 쪽 × 받는 쪽만큼 연결이 늘어난다. 중간에 게시판(브로커)을 두면 서로를 몰라도 된다. 용도별 큐가 여러 개 생기는 문제까지 하나로 합친 것이 카프카.

## 1.2 카프카 입문

### 메시지와 배치

- 메시지: 바이트 배열. 카프카는 내용을 해석하지 않는다.
- 키: 선택값. 같은 키 → 같은 파티션.
- 배치: 같은 토픽·파티션 메시지를 묶어 전송. 처리량 ↑ ↔ 지연 ↑.

### 스키마

JSON은 느슨하고 깨지기 쉬움 → Avro + Schema Registry로 호환성 관리.

### 토픽과 파티션

- 토픽 = 분류 이름, 파티션 = 끝에만 추가하는 커밋 로그, 칸 번호 = 오프셋.
- **순서는 파티션 안에서만 보장.**
- 파티션 분산 → 확장성, 복제 → 가용성.

### 프로듀서와 컨슈머

- 키 있음: `murmur2(key) & 0x7fffffff % 파티션 수` → 같은 키는 같은 파티션. 파티션 수를 바꾸면 매핑이 바뀐다.
- 오프셋 = 컨슈머의 책갈피. 재시작해도 이어 읽음.
- 컨슈머 그룹: **그룹 안에서 파티션 하나는 컨슈머 하나만.** 컨슈머 > 파티션이면 남는 컨슈머는 대기. 다른 그룹은 독립적으로 전부 읽음.

### 브로커와 클러스터

- 브로커 = 서버 한 대. 클러스터 = 브로커 묶음.
- 파티션마다 리더 1 + 팔로워 N. 쓰기/읽기는 리더가, 팔로워는 복제만.
- 보존: 시간 기준 / 크기 기준 / 로그 압착(키별 마지막 값만).

### 컨트롤러

클러스터에 **활성 컨트롤러는 항상 하나**. 데이터(produce/consume)는 다루지 않고 **메타데이터와 리더십**만 관리한다.

하는 일:
1. **브로커 생사 관리** — 브로커가 들어오고 나가는 것을 감지.
2. **리더 선출** — 브로커가 죽으면 그 브로커가 리더였던 파티션마다 ISR(리더를 잘 따라잡고 있는 복제본)에서 새 리더를 뽑는다.
3. **변경 전파** — 바뀐 리더/ISR 정보를 모든 브로커에 알려서, 클라이언트가 새 리더를 찾아가게 한다.
4. **토픽 관리** — 토픽 생성 시 파티션 복제본을 어느 브로커에 둘지 정하고, 삭제·파티션 추가·재할당을 처리.
5. **선호 리더 선출** — 장애 후 한쪽으로 쏠린 리더를 원래 배치(선호 리더)로 되돌림.

```
브로커 2 장애
  → 컨트롤러 감지
  → 브로커 2가 리더였던 P1: ISR [2, 3, 1] 중 살아있는 3을 새 리더로
  → 메타데이터 갱신 → 모든 브로커에 전파
  → 프로듀서/컨슈머가 메타데이터를 다시 받아 브로커 3으로 붙음
```

#### ZooKeeper 모드 (책) vs KRaft (현재)

| | ZooKeeper 모드 (책 2판) | KRaft (Kafka 4.x, 시험) |
|---|---|---|
| 컨트롤러 선출 | 브로커들이 ZK의 `/controller` 임시 노드를 먼저 만드는 쪽이 컨트롤러 | 컨트롤러 노드들(보통 3 또는 5대)이 Raft로 활성 컨트롤러 선출 |
| 메타데이터 저장 | ZooKeeper | 카프카 내부 토픽 `__cluster_metadata` |
| 장애 시 | 새 컨트롤러가 ZK에서 메타데이터를 전부 다시 읽어야 해서 느림 | 대기 컨트롤러가 이미 같은 로그를 갖고 있어 즉시 이어받음 |
| 좀비 방지 | controller epoch | Raft epoch |
| 노드 역할 | 모든 브로커가 컨트롤러 후보 | `process.roles=broker`, `controller`, 또는 둘 다(combined) |

- 컨트롤러 쿼럼은 과반수가 살아야 동작 → 3대는 1대, 5대는 2대 장애까지 견딤.
- 활성 컨트롤러가 메타데이터 변경을 로그에 쓰고, 나머지 컨트롤러와 브로커는 그 로그를 따라 읽는다.

## 1.3 왜 카프카인가?

다중 프로듀서, 다중 컨슈머, 디스크 기반 보존, 확장성, 고성능, 플랫폼 기능(Connect, Streams).

## 1.4 데이터 생태계

활동 추적, 메시지 교환, 지표·로그 수집, 커밋 로그(CDC), 스트림 처리.

## 1.5 카프카의 기원

링크드인 → 2011 오픈소스 → Confluent. 이름은 프란츠 카프카.

## 시험 포인트

- 순서 보장 범위 = 파티션.
- 그룹 내 파티션 : 컨슈머 = N : 1. 컨슈머 수 상한 = 파티션 수.
- 활성 컨트롤러는 클러스터에 하나. 지표 `ActiveControllerCount`의 클러스터 합이 1이어야 정상 (13장).
- KRaft 컨트롤러 쿼럼은 홀수, 과반수 필요.
